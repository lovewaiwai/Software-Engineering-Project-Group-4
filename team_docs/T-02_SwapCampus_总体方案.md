# T-02 SwapCampus 校园闲置物品交易平台总体方案

## 1. 项目定位

SwapCampus 是面向校内师生的闲置物品交易平台，目标是替代分散的微信群和朋友圈交易方式，让二手教材、电子产品、生活用品等闲置物品能够被更高效、更可信地发布、检索、沟通和交易。

核心闭环：

学生实名认证 -> 卖家发布商品 -> 买家搜索/筛选商品 -> 买卖双方站内沟通 -> 买家下单 -> 线下面交确认 -> 双方评价 -> 信用分更新 -> 管理员处理举报与违规商品。

## 2. 范围控制

### 必做功能

- 用户体系：注册登录、学号实名验证沙箱、个人主页、信用分。
- 商品发布：多图、分类、标签、价格、成色、上下架。
- 商品检索：关键词搜索、分类浏览、价格区间、成色筛选。
- 交易流程：下单、取消、模拟支付、面交确认、柜机中转、评价、信用分更新。
- 站内通讯：买卖双方文本/图片/表情聊天，支持交易上下文绑定。
- 后台管理：商品审核、举报处理、用户管理、数据看板。
- 附加项：个性化推荐、AI 自动分类与定价建议、校园柜机中转、信用积分游戏化。

### 降级策略

- 支付不接真实网关，默认实现 Mock 支付适配器，保留真实支付扩展接口。
- 校园柜机/邮件柜不接真实硬件，默认实现 Mock 柜机适配器，支持扫码寄件/取件演示。
- 图片存储优先使用 MinIO；如部署时间紧，可降级为本地静态资源。
- 即时通讯优先 WebSocket；如联调受阻，可降级为短轮询。
- AI 自动分类和定价建议默认使用规则引擎 Mock，不依赖真实 AI 服务。

## 3. 用户角色

- 买家：浏览、搜索、收藏、发起沟通、下单、确认交易、评价。
- 卖家：发布商品、编辑商品、回复咨询、确认面交、查看评价。
- 管理员：审核商品、处理举报、封禁用户、查看运营数据。
- 系统管理员：维护分类、标签、基础配置、审计日志。

## 4. 技术选型

### 推荐主栈

- 前端：Vue 3 + Vite + TypeScript + Element Plus + Pinia + Vue Router。
- 后端：Spring Boot 3 + Spring Security + JWT + MyBatis-Plus。
- 数据库：SQL Server 2022 Developer/Express，使用 SQL Server Management Studio 管理。
- 对象存储：MinIO，本地部署。
- 即时通讯：Spring WebSocket。
- 部署：Docker + Docker Compose。
- 测试：JUnit 5 + Mockito + Postman/Apifox + k6。
- 文档与建模：Markdown/Word + Draw.io/PlantUML。

### 选型理由

- Vue 3 和 Element Plus 适合快速完成交易平台页面和后台管理页面。
- Spring Boot 3 资料丰富，适合课程设计中清晰展示分层架构。
- SQL Server 适合课程环境中通过 SSMS 可视化管理表结构、种子数据和查询结果，能稳定支撑用户、商品、订单、支付、柜机、评价、举报等关系数据。
- MinIO 可以本地模拟对象存储，避免真实云服务依赖。
- WebSocket 能体现实时沟通能力，同时保留短轮询降级方案。

## 7. 关键业务设计

### 订单状态机

```text
CREATED -> SELLER_CONFIRMED -> PAYMENT_PENDING -> PAID -> DELIVERY_PENDING -> RECEIVED -> COMPLETED
```

异常状态：

```text
CANCELLED
REFUNDING
REFUNDED
DISPUTED
CLOSED
```

说明：

- `CREATED`：买家发起下单。
- `SELLER_CONFIRMED`：卖家确认交易意向。
- `PAYMENT_PENDING`：等待支付，线下支付也生成占位支付单。
- `PAID`：模拟支付成功或线下支付确认。
- `DELIVERY_PENDING`：等待面交或柜机中转。
- `RECEIVED`：买家确认收到商品。
- `COMPLETED`：评价后或自动完成。
- `DISPUTED`：交易出现争议，管理员介入。

### 支付与柜机默认接口

- 支付采用 `PaymentAdapter`，默认 `MockPaymentAdapter` 生成模拟支付单、支付链接和退款流水。
- 柜机采用 `LockerAdapter`，默认 `MockLockerAdapter` 生成柜机任务、寄件二维码文本、取件码和柜门号。
- 两类接口只影响支付和交付子流程，不改变商品、订单、评价的核心数据结构。

### 附加项设计口径

- 个性化推荐：基于浏览、收藏、订单和分类偏好的加权推荐。
- AI 分类定价：基于关键词与同类商品均价的 Mock 建议。
- 柜机中转：支持预约柜门、扫码寄件、扫码取件。
- 信用积分游戏化：信用分和游戏化积分分离，支持签到、任务、兑换虚拟权益。

### 信用分规则

默认信用分：60。

加分：

- 完成交易：+2。
- 获得好评：+1。

扣分：

- 被有效举报：-5。
- 发布违规商品：-10。
- 爽约或恶意取消：-3。

信用分所有变化必须写入 `credit_records`，保证可追溯。

### 举报审核

流程：

买家/卖家举报 -> 系统记录举报 -> 关键词辅助标记 -> 管理员审核 -> 处理商品或用户 -> 写入审计日志。

处理结果：

- 驳回。
- 商品下架。
- 用户警告。
- 用户封禁。

## 10. 答辩演示脚本

1. 管理员配置商品分类和审核规则。
2. 卖家登录并发布一个二手商品。
3. 管理员审核商品通过。
4. 买家通过关键词和分类筛选找到商品。
5. 买家收藏商品并进入聊天。
6. 买卖双方沟通后买家下单。
7. 卖家确认交易，双方完成线下面交。
8. 买家评价，系统更新信用分。
9. 演示举报违规商品，管理员处理并查看审计日志。

## 11. 最小可交付标准

- 能通过 Docker Compose 或本地服务启动前端、后端、SQL Server 和 MinIO。
- 至少包含买家、卖家、管理员 3 类角色。
- 至少包含 30 名虚拟用户、200 条商品种子数据、20 条交易记录。
- 主流程无断点：实名 -> 发布 -> 审核 -> 检索/推荐 -> 沟通 -> 下单 -> 模拟支付 -> 面交/柜机 -> 评价。
- 核心规则有测试：订单状态机、信用分更新、支付 Mock、柜机 Mock、举报审核。
- 有接口测试记录和基础性能测试结果。
